FILE B10 · §1 · B10.1 · Checkout success

B10.1 · You're on Pro

Post-Checkout redirect from Stripe after first upgrade or plan change. Welcoming, brief, forward — primary CTA returns the user to the dashboard so they can immediately use the new plan; secondary takes them to /account/billing (A7.2 Plan & billing card) to see the receipt and confirm the line items. The plan-name string ("Pro") is templated — A6 and A7.2 already render it as a placeholder; B10.1 picks up the same convention so a code-agent doesn't invent a new string format.

FILE B10 · §1 · B10.2 · Checkout cancelled

B10.2 · Checkout cancelled

User bailed mid-Checkout — closed the Stripe modal, hit back, or completed it but cancelled. Recoverable, not a fault. Page leads with reassurance ("no charge made") to pre-empt the panic question, then offers two equally-balanced paths: try again or return to dashboard. Neutral arrow-left icon (NOT a warn-icon) — this is a calm "you can leave or you can retry" page, not an error state.

  • Neutral icon, not warn. arrow-left in --ink-3 (the lifted .err-icon-tile's default color) — recoverable state, no alarm. Using alert-triangle here would imply a fault; cancelling is a normal action a user might take many times before committing.
  • "No charge made" lives in the FIRST sentence. Pre-empts the user's first thought ("did they take my money?") before they get to anywhere else. Trust beats brevity in transactional flows.
  • "Try again" is primary, not "Back to dashboard". Stripe Checkout cancellation is most often a stumble (modal closed accidentally, payment-method browse), not an explicit reject. Putting Try-again first matches the typical retry intent. A user who really wants out has the secondary text-button right there.
  • Same B2 chrome as B10.1. Card geometry, padding (40/32), icon-tile invisibility, and CTA-stack max-width 280px are byte-identical to B2.1 / B2.2 / B2.3 / B4.7 / B10.1. Visual continuity tells the user "same product, different state," not "I navigated to a different surface."

B10.3 · Plan-name placeholder strategy

B10.1 templates the plan name ("Pro") with the same convention A6 and A7.2 already use. This block is annotation-only — visually documents the placeholder pattern in one place so a code-agent wires the same string-substitution everywhere it appears.

You're on Pro
Same headline shape as A7.2 — visual continuity confirms to the user "this is the same product showing me the same plan name". Bold span .plan wraps the substring.
  • One templating contract across three surfaces. A code-agent wiring this should treat .plan (B10.1) and the equivalent bolded substrings in A6 / A7.2 as the same template variable. Renaming to {{ planName }} or $planName in HTML is fine — what matters is they all render the SAME string at the SAME time.
  • Free-plan edge case. If a user lands on B10.1 immediately after a downgrade (Pro → Free), the headline "You're on Free" reads correctly. No special-case markup needed; the placeholder absorbs it.
  • Plan-string source-of-truth. Read from Supabase user record's stripe_plan_name column (synced from Stripe webhook). If the column is null or a stale value, fall back to "Pro" — this surface is reached only via successful Checkout, so a non-null value is expected.

Why standalone (no app chrome)

  • Pre-hydration timing. Both routes render in the brief moment between Stripe redirect and Vue Router hydration of the dashboard shell. Sidebar and topbar haven't loaded yet.
  • Mental-model handoff. User just left a Stripe-branded surface; a calm centered card says "you're back" without forcing them to parse a sidebar.
  • Same chrome family as B2 + B4.7. Both error pages and auth bridges use this card pattern. Stripe returns are also a "bridge" surface — different content, same chrome.
