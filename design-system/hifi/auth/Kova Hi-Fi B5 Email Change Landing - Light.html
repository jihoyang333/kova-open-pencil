  • Inline icon, not a medal. A15.06's .auth-medal ok (48×48 circle with border) is used for post-signup celebration; an email change is a smaller event that doesn't earn the same celebration. 24×24 inline check-circle in --accent per handoff §6.2.
  • New email is bolded inline, not blocked off in a row pattern. The address IS the news — user wants to scan it, confirm correctness, and move on. Bold via <b>; no new typography.
  • "We've also sent a notification to your previous email" — security best-practice messaging. Tells the user the change is reversible from their old inbox if it wasn't them. The "Revert email change" foot link gives the same affordance to the new owner if they were spoofed.
  • Long email wrap. The longer email jiho.yang+work@studiocollective.co tests wrap behavior — the auth-card max-width 380px keeps the bold address on one line at desktop, gracefully wraps at narrow viewports. Verified via screenshots at 1440 + 375.

  • Same shell, reframed copy. Card geometry, typography, button hierarchy are identical to B5.1 — only the icon glyph + color, the headline, and the sub-line change. Visual continuity tells the user "you're still on the same path, this just didn't go through."
  • Account still on old email. The sub-line explicitly tells the user the change DIDN'T happen — important because they might assume "the link expired" means "the change rolled back." It never went through in the first place.
  • Single CTA. The recovery is at A7.1, not here — sending the user back to settings to re-request keeps the verify-flow honest (each request gets its own time-bound link).
  • Clock in --ink-3 rather than --warn because warn currently degrades to --ink-2 per design.md §5 ban 12 — using --ink-3 directly preserves the dim-edge intent without competing with the rest of the chrome's secondary text in --ink-2.

B5 · notes
  • Theme isolation. Light only — root <html> carries no dark-mode attribute, no dark-mode tokens referenced. Email-change verification happens in the user's authenticated context, but the verify-link landing is pre-app: light auth chrome is the right place per the Figma model.
  • Auth-card chrome lifted from A15 per handoff §3.8. The A15 inline <style> block is reproduced byte-for-byte; the lifted block is unmodified.
  • One extension class: .auth-icon + .auth-icon.ok + .auth-icon.dim for the 24×24 icon-above-headline ornament (smaller than B2's 48×48 error tile per handoff §6.2). Plus .auth-card.icon-led for the alignment override. All append below the lifted block.
  • Distinct from A15.06. A15.06 is the post-signup magic-link return — uses .auth-medal ok (48×48 medal) and routes to onboarding/dashboard. B5.1 is post-A7.1-email-change — uses .auth-icon ok (24×24 inline) and routes back to /account/profile. Different events deserve different ornaments.
  • Wrap test. B5.1 uses a long email (jiho.yang+work@studiocollective.co) so wrap behavior is exercised. Card max-width 380px holds at desktop; gracefully reflows at narrow viewports.
  • Open wiring questions (flag for engineering): (a) Does the 24-hour expiry come from Supabase's email-change token TTL or an app-side gate? (b) Does the "Revert email change" link auto-rollback on B5.1 if the previous owner clicks it, or does it route through a confirm step? Recommend confirm step (irreversible action).
