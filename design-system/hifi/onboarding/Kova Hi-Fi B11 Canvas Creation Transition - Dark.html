Canvas creation transition · B11.1 · B11.2 · B11.3 · B11.4

The 0.5–3 second window between submitting a prompt in the dashboard composer and landing on the new canvas. Without this state, the composer freezes mid-action and the user can't tell if the click registered. Four snapshots across the transition arc: idle (reference) → submitting → almost-there → splash hand-off. Dashboard chrome (sidebar / topbar / content / composer wrap) is LIFTED from batch-a/dark/Kova Hi-Fi 03 Brand Dashboard - Dark.html per CHUNK_3 §3.8; only the composer INTERIOR changes between B11.1 / B11.2 / B11.3 — chrome dimensions stay byte-identical so the page never reflows.

FILE B11 · §2 · B11.2 · Composer submitting

B11.2 · Composer submitting

User just clicked Generate. The prompt is in flight (POST /api/canvases creating the row + initializing the Yjs doc). Same chrome as B11.1 byte-identical — only the composer interior changes: input goes read-only with prompt text dimmed slightly (--ink-2); the arrow-right in the submit button is replaced inline by Lucide loader-2 spinning at 14×14; the caption "Creating canvas…" fades in below the wrap. The wrap dimensions, borders, and 14px radius do not move — preserving the user's reference point.

  • Long prompt wraps to 2 lines, wrap height grows. The input has min-height: 56px in the lifted styling — 1-line prompts sit at 56px, 2-line prompts grow naturally. The wrap padding (18/20/12) absorbs the extra height; chips below stay aligned to wrap-bottom.
  • Spinner replaces arrow inline. The submit button slot keeps its 999px-pill outer chrome (.go-spin mirrors .btn.accent.go geometry) so the wrap right-edge doesn't shift. Lucide loader-2 spins via CSS cv-spin 1s linear infinite — declared at file scope, no token redefinition.
  • "Creating canvas…" appears via 200ms fade-in. The fade prevents a layout-shift "pop" — first-time users notice subtle motion as feedback. The caption is --t-meta (11.5px) ink-3 to read as a quiet status line, not a heading.
  • Attach button disabled. No + attachments mid-submit. The native disabled attribute carries the affordance; styling stays the canonical .composer-input-tools .attach.
  • Chips remain visible but unaffected. They're click-targets a returning user might use after the submit completes; no need to dim them. They stay in idle styling.
FILE B11 · §3 · B11.3 · Composer transition (almost there)

B11.3 · Almost there — main content fading to canvas

Canvas record was created server-side, Yjs doc is initializing, redirect to the new canvas is imminent (≤500ms). Same chrome as B11.1 / B11.2; the composer interior swaps to a quiet "review" line of the original prompt (the user can confirm what they submitted), the caption swaps to the prompt-echo + accent check-tick, and the entire main-pane content area fades to 0.5 opacity. Sidebar + topbar stay full-opacity so the user has a stable reference point — they're not lost in the transition, just told "we're handing you off."

  • Content fades, sidebar + topbar don't. .content.transition-fade (extension class layered below the lifted .content) drops opacity to 0.5 + disables pointer-events so the user can't accidentally click chips during the redirect. The sidebar and topbar stay full-opacity — the user is still anchored in the same brand, the same nav state, the same crumb. Only the workspace below has shifted.
  • Prompt is preserved as a review line. The original typed text becomes a quiet --ink-2 read-only line (the same paragraph weight Klaviyo email subjects use). Confirms the prompt wasn't lost mid-submit — important for first-time users who fear the submit "ate" their words.
  • Status caption swaps to the prompt-echo + accent check. "Spring drop teaser · Wildgrove · ready" with a small --accent tick. The accent earns its appearance here because the canvas IS ready — handing the user off to a successful state. (Same accent rule as design.md §1.1: one accent, used for affirmative selection / completion.)
  • Spinner stays on the submit button. Even though the canvas is "ready," the spinner doesn't switch to a check-icon — the spinner represents the redirect, which IS still in flight. When the redirect lands, the canvas page replaces this surface entirely; users never see the spinner finish.
FILE B11 · §4 · B11.4 · Hand-off splash

B11.4 · Opening canvas… (full-viewport hand-off)

Brief moment between dashboard fade-out and canvas-page mount. Full viewport, no app chrome — same dark plate (--bg) the canvas itself uses, so the splash → canvas transition reads as "I'm already on the canvas, content is loading" rather than "another page loaded." Centered Lucide loader-2 spinner + caption "Opening canvas…". Lasts ≤500ms in production; designer call to include this scene per CHUNK_3 §6.1 — including it makes the full transition arc explicit for the implementer (B11.1 → B11.2 → B11.3 → B11.4 → canvas mount).

B11.4 · hi-fi
Opening canvas…
  • Designer-called: included. CHUNK_3 §6.1 flagged B11.4 as optional. Including it makes the implementer's transition map explicit: B11.1 (idle) → B11.2 (submit, ~600ms) → B11.3 (almost-there, 240ms fade) → B11.4 (splash, ≤500ms) → canvas-mount. Without B11.4 the implementer has to invent the splash; with it, the visual is locked.
  • Same dark plate as the canvas itself. Splash bg = --bg — the canvas-plate token from design.md §1.1. The splash → canvas transition appears as "the canvas was always there, the content just hadn't loaded" rather than "a different page loaded then jumped." Visual continuity beats any ergonomic gain from a colored splash.
  • No mark, just spinner + caption. User just left a Kova-branded surface (B11.3) — restating the brand here adds nothing. Spinner alone keeps the splash quiet; caption carries the verb.
  • ≤500ms total budget. If the canvas isn't ready in 500ms, the spinner has done its job and the user is now waiting on a slow load — not a transition. At that point, the canvas page should mount with its OWN skeleton state (out of scope here; lives in Batch B). B11.4 is the bridge, not the destination.

Chrome byte-identity check (B11.1 / B11.2 / B11.3)

  • Sidebar. Same canonical declaration; same brand-switch + side-search + nav children across all three scenes.
  • Topbar. Same breadcrumb + actions; "New canvas" button stays clickable (transition doesn't disable global nav).
  • Composer wrap. Same 14px radius, same 18/20/12 padding, same 760px max-width. The submitting + review states only change the inner span's ink color; chrome dimensions never shift.
  • What DOES change between scenes: input-state class on .composer-input (idle / submitting / review); submit-button content (arrow / spinner); caption presence (none / "Creating canvas…" / "ready" + tick); main-pane opacity (1 / 1 / 0.5).

Out of scope / deferred

  • Failure-mode states (canvas-create POST 500, network drop mid-submit). Belongs to B2 error pages or a B11.5 follow-up; out of scope here.
  • Slow-load skeleton if canvas takes >500ms to mount. Lives in Batch B (canvas-side) — splash hands off there.
  • Optimistic preview (showing partial canvas during creation). Out of scope; current backend creates canvases atomically.
